# Временный журнал оптимизации live pipeline

Статус: план экспериментов. Документ ведётся до завершения итераций; после этого краткие подтверждённые выводы будут перенесены в `IMPLEMENTATION_PLAN.md`, а этот файл удалён.

## Исходный замер

Замер `live #991` с включённым сглаживанием метрик за секунду:

- Pipeline FPS: `25,6`;
- end-to-end latency: `37,8 мс`;
- GPU → CPU copy: `6,2 мс`;
- очередь live: `6,2 мс`;
- preprocess: `11,7 мс`, в том числе BGRA → BGR `1,6 мс`, letterbox `2,1 мс`, Tensor `8,0 мс`;
- ONNX inference: `12,5 мс`;
- postprocess: `0,1 мс`;
- median: `39,1 мс`, p95: `45,5 мс`.

Данные получены на стабильном пути `Windows.Graphics.Capture → D3D11 staging texture → Map → BGRA32 buffer → CPU preprocessing → ONNX Runtime DirectML`. Эксперимент `D3D11On12 → D3D12/DirectML` не возобновлять в рамках этих итераций: он зафиксирован как нестабильный в `IMPLEMENTATION_PLAN.md`.

## Правила измерения

- Сравнивать только прогретые значения median и p95 одного сценария live capture.
- Фиксировать активный ONNX backend, разрешение входа, выбранную модель, preview-настройки и целевой FPS захвата.
- Проверять, что найденная OBB и deployment gate не стали хуже на smoke-наборе.
- После каждой итерации записывать фактическое изменение, решение и причину в этот документ.

## Итерации

### 1. Throttle до GPU → CPU readback

Статус: отменено после smoke-теста.

Отбрасывать ненужные кадры в `FrameArrived` до staging `CopyResource → Map → memcpy`, но освобождать `Direct3D11CaptureFrame` сразу. Цель — не выполнять дорогой readback кадров, которые всё равно будут вытеснены bounded latest-frame queue.

Проверенный вариант: queue была заменена на `Wait` с ёмкостью один кадр. Пока в ней был CPU buffer, следующий `Direct3D11CaptureFrame` извлекался и освобождался без staging readback.

Результат: smoke-тест показал рост `Очередь (live)` примерно до `35 мс`. Причина — detector получал первый ожидающий CPU-кадр, а более свежие кадры больше не могли вытеснить его. Вариант удалён; восстановлена bounded latest-frame queue с `DropOldest`.

Вывод: для live-режима свежесть кадра важнее сокращения readback. Следующая попытка должна хранить последний кадр на GPU и выполнять CPU readback только для текущего запроса detector, не оставляя устаревший CPU buffer в очереди.

### 2. Один проход для Tensor

Статус: отменено после smoke-теста.

Заменить цепочку `BlobFromImage → Marshal.Copy → DenseTensor<float>` на предвыделенный buffer с одним проходом BGR → RGB, нормализацией и раскладкой CHW. Не менять контракт ONNX input.

Проверенный вариант: при загрузке ONNX создавались один `float[]` и связанный с ним `DenseTensor<float>`. На каждом кадре buffer напрямую заполнялся из BGR `Mat` в RGB/CHW с нормализацией `1/255`; промежуточный OpenCV float blob и его копирование в managed memory удалялись.

Результат: smoke-тест не показал изменения `Tensor`, median или p95 — Tensor остался около `8 мс`. Вероятная причина: `BlobFromImage` выполняется оптимизированным native OpenCV, а прямой scalar-проход C# не даёт выигрыша, несмотря на отсутствие лишней копии. Вариант удалён, восстановлен исходный OpenCV preprocessing.

Вывод: не усложнять preprocessing без измеримого выигрыша. Следующая итерация должна менять число проходов по пикселям или размер обрабатываемой области, а не только заменять native реализацию на managed цикл.

### 3. Объединение letterbox и подготовки Tensor

Статус: запланировано после итерации 2.

Исследовать запись resize/letterbox непосредственно в целевой Tensor либо иной вариант без полного промежуточного BGR/letterbox buffer. Выполнять только если итерация 2 не даёт достаточного результата.

Критерий успеха: снижаются суммарные Letterbox + Tensor при идентичной геометрии transform и идентичном detector output на контрольных кадрах.

### 4. Эксперимент с меньшим input size

Статус: запланировано после CPU-оптимизаций.

Текущий ONNX export имеет статическую форму, поэтому для `768 × 768` или `640 × 640` нужен отдельный ONNX export. Переобучать модель для первого измерения не обязательно: сначала экспортировать тот же `best.pt` с новым `imgsz`, затем сравнить Test и smoke-набор. Переобучение с этим `imgsz` потребуется только при заметной потере качества или если такой вариант будет выбран для финальной модели.

ONNX — формат модели для inference, а YOLO — архитектура/семейство модели. Обычно последовательность такая: обучить YOLO OBB, экспортировать её checkpoint в ONNX и использовать ONNX в приложении. Один и тот же checkpoint можно экспортировать в несколько ONNX-артефактов с разными статическими `imgsz`; каждый из них нужно проверить по качеству и скорости.

Критерий успеха: `768` или `640` заметно сокращает preprocess и inference, сохраняя приемлемые результаты Test и smoke-набора. Начинать с `768`. Размер выбирается в блоке обучения при экспорте ONNX; отдельное обучение для первой проверки не требуется.

### 5. Tracking и редкий полный inference

Статус: отложено.

После появления надёжного tracker запускать полный YOLO OBB раз в несколько кадров, а между запусками обновлять положение панели tracker’ом. До tracker нельзя пропускать inference, потому что положение OBB между кадрами не обновляется.

Критерий успеха: снижение нагрузки на detector без дрейфа OBB и без задержки восстановления после потери панели.

### 6. ROI inference после первого обнаружения

Статус: отложено.

После успешного full-frame поиска использовать область вокруг предыдущей OBB с запасом; при снижении confidence, выходе OBB за границы ROI или смене сцены возвращаться к full-frame поиску. Это отдельная стратегия выполнения уже обученной YOLO-модели, а не замена YOLO на ONNX.

Критерий успеха: ускорение preprocessing и inference при сохранении качества; полный поиск надёжно восстанавливается после потери панели.
